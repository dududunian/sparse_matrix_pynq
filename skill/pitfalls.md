# 失败与观察的提炼记录

这里区分本队已经发生的问题与一般预防性检查；不将未发生的情形编造成开发记录。

## 1. 仿真正确不能代替实际时序

- 来源：本项目原始 100 MHz 全设计实现出现 setup WNS -0.876 ns；50 MHz 条件下复核为 +9.124 ns，hold 为 +0.011 ns。属于实现工具的结果，尚非板上频率或性能实测。
- 触发：功能仿真通过后直接按名义频率交付；只看早期综合估计。
- 提炼：运行频率必须对应真实实现证据，分别记录综合、布局布线、板测的结论。
- 排查：查周期约束和未约束路径 → 查 setup/hold → 查实际时钟树 → 核对运行设置。
- 验证：在自己的实现报告中核对上述条件；本包不提供跨版本时序报告自动解析器。
- 边界：换设计/换器件后重新实现。不能复用本队 50 MHz 数值。

## 2. 加载时钟与运行时钟可能不一致

- 来源：本队交付 HWH 保留名义 100 MHz，运行程序在内核空闲时设置并核对 50 MHz。
- 触发：绕过配套加载程序，仅使用 HWH 自动配置后直接开始计算。
- 提炼：Overlay 加载、时钟设置和任务启动应形成有明确前置条件的流程。
- 排查：查 HWH 时钟元数据 → 查实际驱动内核的时钟 → 确认空闲/复位 → 设定并读回 → 再启动。
- 已验证效果：本队驱动的软件测试检查频率不符时拒绝启动；真实时钟行为仍待板上确认。
- 边界：自动启动内核、多时钟域或无法运行时调频的设计需要其他策略。不能普遍套用加载后调 PL0。

## 3. 历史输出与当前源码重新运行的结果不能混为一谈

- 来源：本队重新运行 28 个案例时，原代码 27/28 匹配，某跨块案例有 5 个输出错误；后续修复后全量回归通过。
- 触发：沿用压缩包里保存的旧结果作为当前代码通过的证据。
- 提炼：比较当前运行产生的全量输出，并保存输入、源码/构建身份与日志；对边界案例建立回归。
- 排查：确认输出来源 → 比较全部长度和值 → 找到首个差异及坐标 → 追踪握手和状态 → 修复并重跑。
- 已验证效果：本包比对器会拒绝长度差异、空输出和数值差异，并用故障注入用例验证；不声称由新脚本首次发现了原始 RTL 缺陷。
- 边界：比对器不证明 Golden 本身正确，也不替代协议和控制流验证。

## 4. 连续任务需要新的完成证据

- 来源：本队驱动增加完成计数递增检查，避免上次完成锁存/旧输出导致误判；属于设计审查后加入的预防措施，不宣称发生过真实板故障。
- 触发：done 是锁存位，第二次任务只轮询 done，没有清除或任务身份检查。
- 提炼：按硬件协议清除旧状态或校验新任务计数；设置超时并记录错误。
- 已验证效果：本队主机侧 mock 测试和 AXI 联合仿真覆盖连续任务；新板仍需独立实测。
- 边界：计数器溢出、清零和启动接受规则需从实际设计确定。

## 5. 平台判定不应写死 aarch64

- 来源：从项目专用 ZCU104 环境脚本提炼时观察到原判定与单一架构绑定；这是通用化审查发现，不是第二块板已启动成功。
- 提炼：环境采集保留 machine、板型及各项 API 导入结果，不把 32 位 ARM PYNQ 排除。
- 验证：已用 mock 覆盖 armv7l/aarch64 和 API 部分缺失；Windows 无 PYNQ 时也可产生报告。
- 边界：架构字符串与导入成功不能证明 PL 下载、MMIO 权限或驱动兼容。
